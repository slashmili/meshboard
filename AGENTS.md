# Product Requirements: Meshboard (P2P Encrypted Whiteboard)

## 1. Summary

A peer-to-peer, end-to-end encrypted collaborative whiteboard for teams
sharing ideas on calls. One person creates a board; others join via a
link or QR code and draw together in real time. No account, no central
server storing board content, no persistence beyond the session unless
a participant explicitly exports.

Target platforms: Web, iOS, Android, Linux, macOS, Windows.

## 2. Non-Goals (v1)

- Large group sessions (design target: up to ~8 concurrent peers, full mesh)
- User accounts, auth, or identity beyond "whoever has the link"
- Cloud storage or server-side persistence of board content
- Per-user access revocation within a live session (shared-secret model)
- Web target for the native-app codebase (web stays a separate TS implementation)

## 3. Architecture Overview

**Monorepo layout** (suggested):
```
/packages/web          - TS + React (or similar) + Yjs + y-webrtc
/packages/native        - Kotlin Multiplatform + Compose Multiplatform
                          (Android, iOS, Desktop: Linux/macOS/Windows)
/packages/crdt-core      - yrs (Rust) bindings consumed by /native
/packages/signaling      - thin signaling server (WebSocket relay)
/packages/shared-protocol - wire format docs / schemas shared by web & native
```

**Sync core**: CRDT-based, no single host after board creation.
- Web: Yjs
- Native: `yrs` (Rust port of Yjs) via KMP interop, so wire format is
  compatible with Yjs updates from web peers.

**Transport**: WebRTC data channels, full mesh (every peer connects to
every other peer directly).
- Web: `y-webrtc` provider
- Native: platform-native WebRTC bindings (`libwebrtc` on
  Android/Desktop, native WebRTC framework on iOS) implementing the
  same signaling/data-channel protocol as `y-webrtc`, so web and
  native peers can mesh together.

**Signaling server**: minimal WebSocket relay. Only exchanges ICE
candidates / session descriptions to establish P2P connections. Never
sees board content (plaintext or ciphertext).

**TURN relay**: fallback for peers behind restrictive NATs/firewalls
(common on corporate networks). Forwards encrypted bytes only; cannot
read content. Required for real-world reliability — not optional
infrastructure.

**No host after creation**: the peer who generates the QR code has no
special runtime privileges once the session starts. Every peer holds
full CRDT state. Any peer (including the creator) can disconnect at
any time with zero impact on the others.

## 4. Security Model

- **Session key**: symmetric key (AES-256-GCM) generated by the
  creator at board creation. Encoded in the QR code / URL fragment
  (`#key=...`) — never sent to or through the signaling server.
- **Scope**: one key per session, shared by all participants. Anyone
  with the link can decrypt the full board, past and future, for the
  life of that session. No per-slide/per-message forward secrecy —
  this is a deliberate trade-off for usability (late joiners see full
  history).
- **Transport authentication**: WebRTC DTLS certs are ephemeral by
  default (auto-generated per connection). The cert fingerprint should
  be embedded in the QR code and verified by joining peers before
  trusting the data channel, to prevent MITM via a compromised
  signaling server. The QR code (scanned out-of-band) is the sole
  source of truth for both the session key and the fingerprint — never
  relayed through the signaling server.
- **At rest**: no server-side storage of board content, encrypted or
  not. Signaling/TURN servers only ever handle ciphertext or
  connection metadata in transit.
- **Session end**: when the last peer disconnects, board state is
  gone. No recovery unless a peer exported before leaving.

## 5. Phased Delivery

### Phase 1 — Minimal cross-platform system
- Board creation can be initiated from any platform (web or native) —
  there is no "web-only" or "native-only" restriction on who starts a
  session, since no platform holds special host privileges.
- Board creation on any platform generates a shareable link + QR code.
- Joining via link or QR code opens the same board on another
  device/platform.
- Basic real-time drawing sync between peers (no CRDT yet — simplest
  possible live sync to validate the cross-platform pipe end to end).
- Base drawing toolset: freehand pen, eraser, basic shapes
  (rectangle/circle/line), pan/zoom canvas.
- WebRTC connection established directly between peers via the
  signaling server; TURN fallback wired in from the start (not deferred).
- Runs on Web, iOS, Android, Linux, macOS, Windows.
- **Exit criteria**: two peers on two different platforms (e.g., one
  web, one desktop) can draw on the same board in real time.

### Phase 2 — CRDT integration
- Replace naive sync with Yjs (web) / `yrs` (native), validated for
  wire-format compatibility across platforms.
- Full-mesh peer connections (not host-relayed).
- Host migration behavior: verify that if the creator leaves, all
  other peers continue uninterrupted (this should fall out naturally
  from full mesh + CRDT, but must be explicitly tested).
- Late-joiner flow: new peer connects to any existing peer, receives
  full document state via CRDT sync.
- Peer disconnect/reconnect handling (temporary network drop vs. leaving).
- **Exit criteria**: 4+ peers across mixed platforms can join, draw
  concurrently, have one peer (including the creator) drop and
  rejoin, and all converge on the same board state.

### Phase 3 — End-to-end encryption
- Session key generation, QR/link encoding, key never touching
  signaling infrastructure.
- Encrypt/decrypt CRDT updates at the application layer before they
  hit the data channel.
- DTLS fingerprint verification against QR-embedded value on join.
- Confirm signaling and TURN servers only ever see ciphertext.
- **Exit criteria**: packet capture on signaling/TURN traffic shows no
  recoverable board content; a peer without the correct link/key
  cannot join or read the session.

### Phase 4 — Feature expansion
- Expanded drawing tools: text boxes, sticky notes, connectors/arrows,
  image insertion, multi-select/move, undo/redo (CRDT-aware).
- Light/dark mode: follow system setting by default, with explicit
  user override, on all platforms.
- Export: save board as PNG/PDF and as a native snapshot format that
  supports re-import.
- Import: reopen a previously exported snapshot to continue drawing
  in a new session (new QR/link/key, since the old session is gone
  once peers disconnect).
- Presence indicators: show connected peers, live cursors/names.
- support Pressure-sensitive stylus in all platforms
- store session and metadata(keys and certificartes) in localstorage
for web and local storage on native platform to resume the drawing

## 6. Open Questions for Implementation

- Exact peer cap for full mesh before UX degrades (target ~8; needs
  validation under real network conditions).
- Snapshot/export format: proprietary JSON (wrapping Yjs/yrs state) vs.
  a documented open format.
- Whether TURN infrastructure is self-hosted or a managed provider.
- Minimum OS/browser versions per platform.
- Deep-linking (custom URL scheme / universal links / app links) so a
  shared link opens directly in the native app when installed,
  falling back to web otherwise. Not required for Phase 1 — plain
  HTTPS links with a web fallback are sufficient to start; deep-linking
  can be layered in later (candidate for Phase 4 or a later pass)
  without changing the underlying architecture.
